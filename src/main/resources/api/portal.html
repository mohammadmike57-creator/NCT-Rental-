Sandbox and production

The same addresses serve both. Your credentials decide the environment, so test code goes live by changing credentials only.

Sandbox tests

Real availability and prices, but bookings are kept apart: they never reach our branches and never hold a car. Use the test API key, or an OAuth client marked sandbox.

Production live

Confirmed bookings go straight to the branch. Production credentials are issued after certification.

Credentials are sent on request, and never in the same email as this documentation. Keep them on your server only, never in a browser or mobile app.

Authentication

XML and SOAP: API key

Send the key in the X-Api-Key header, or as Authorization: Bearer <key>, or inside the message as POS/Source/RequestorID@MessagePassword. Ten failed attempts from one address within 10 minutes lock it out for 15 minutes.

REST v3: OAuth 2.0 client credentials

Exchange your client ID and secret for a 30-minute bearer token at __BASE__/oauth/token. Each client has scopes: locations:read, fleet:read, availability:read, quotes:read, reservations:read, reservations:write, inventory:read, webhooks:manage.

curl -s -X POST __BASE__/oauth/token \
  -u "$CLIENT_ID:$CLIENT_SECRET" \
  -d grant_type=client_credentials

Conventions

Envelope

Every JSON answer has status, requestId, correlationId, apiVersion, timestamp, environment, then data or error.

Correlation

Send X-Correlation-ID and we use it in our logs and in the answer; every answer carries X-Correlation-ID and X-API-Version.

Idempotency

Bookings, changes and cancellations need Idempotency-Key (up to 100 characters). The same key returns the first result.

Time and money

Times are branch local time (Asia/Amman). Amounts are decimals in the currency shown; the breakdown always adds up to the total.

OpenTravel releases and answer layout

Answers use the OpenTravel 2003/05 namespace, which every release from 2003 to 2024 shares. Two layouts are available per connection; we agree which one with you.

LayoutWhat you getBest for
StandardEvery answer is valid against the official OpenTravel XML schemas (checked for 2010B, 2014B and 2017B), with OpenTravel code lists for charges and coverages.New connections and platforms that validate against the schemas
As connectedThe layout agreed with existing partners, with extra details (deposit, excess, cancellation deadline) in TPA_Extensions.Connections that are already live

Requests are checked against the OpenTravel 2017B schema. By default a request that does not match is still answered and we tell you what to fix during certification; when agreed, the connection can refuse such requests with error 321.

Signed requests (optional)

When signing is agreed for your channel, add two headers to every XML request: X-URD-Timestamp (Unix seconds) and X-URD-Signature: sha256=<hex HMAC-SHA256(secret, timestamp + "." + body)>. The body is the exact bytes you send. Requests older than 5 minutes, or seen before, are refused.

Webhooks v2

Subscribe an HTTPS address with POST /api/v3/webhooks/subscriptions. Events: reservation.created, .confirmed, .modified, .cancelled, .no_show, .picked_up, agreement.created, agreement.closed, inventory.updated. Send POST …/{id}/test for a webhook.test event.

HeaderMeaning
URD-Webhook-IdUnique per event; store it and ignore repeats
URD-Webhook-EventEvent name
URD-Webhook-Timestamp · URD-Webhook-NonceUnix seconds and a random value
URD-Webhook-Signaturev1=<hex HMAC-SHA256(secret, id.timestamp.nonce.body)>; two values, comma separated, for 72 hours after a secret rotation

Delivery and retries

Answer with any 2xx within 10 seconds. Otherwise we retry after 1, 5, 15, 60, 180 and 360 minutes, then every 12 hours, for 72 hours. Events about the same reservation arrive in order. After 72 hours the event moves to the dead-letter list, where POST /webhooks/deliveries/{id}/replay sends it again.

Verify a webhook

const crypto = require('crypto');
function verify(req, secret) {             // req.rawBody: the body exactly as received
  const id = req.get('URD-Webhook-Id'), ts = req.get('URD-Webhook-Timestamp'), nonce = req.get('URD-Webhook-Nonce');
  if (Math.abs(Date.now() / 1000 - Number(ts)) > 300) return false;
  const expected = 'v1=' + crypto.createHmac('sha256', secret).update(`${id}.${ts}.${nonce}.${req.rawBody}`).digest('hex');
  return req.get('URD-Webhook-Signature').split(',').some(s =>
    s.trim().length === expected.length && crypto.timingSafeEqual(Buffer.from(s.trim()), Buffer.from(expected)));
}
import hmac, hashlib, time
def verify(headers, raw_body: bytes, secret: str) -> bool:
    i, ts, nonce = headers["URD-Webhook-Id"], headers["URD-Webhook-Timestamp"], headers["URD-Webhook-Nonce"]
    if abs(time.time() - int(ts)) > 300:
        return False
    msg = f"{i}.{ts}.{nonce}.".encode() + raw_body
    expected = "v1=" + hmac.new(secret.encode(), msg, hashlib.sha256).hexdigest()
    return any(hmac.compare_digest(s.strip(), expected) for s in headers["URD-Webhook-Signature"].split(","))
function verify(array $h, string $raw, string $secret): bool {
  $id = $h['URD-Webhook-Id']; $ts = $h['URD-Webhook-Timestamp']; $nonce = $h['URD-Webhook-Nonce'];
  if (abs(time() - (int)$ts) > 300) return false;
  $expected = 'v1=' . hash_hmac('sha256', "$id.$ts.$nonce.$raw", $secret);
  foreach (explode(',', $h['URD-Webhook-Signature']) as $s) if (hash_equals($expected, trim($s))) return true;
  return false;
}
static bool Verify(IHeaderDictionary h, string raw, string secret) {
    string id = h["URD-Webhook-Id"], ts = h["URD-Webhook-Timestamp"], nonce = h["URD-Webhook-Nonce"];

Certification and go-live

  1. We create your channel and code, and send sandbox credentials on request.
  2. You connect in the sandbox: search, book, retrieve, modify and cancel; webhooks if you use them.
  3. You send us the references of your test bookings; we check them on our side.
  4. We agree rates, cancellation terms and the payment model, and issue production credentials.
  5. First live bookings are monitored together; then you are live.
